## 2. Чи усунуто проблему з опису

### Завдання 1 — Factory Method
- [x] Процедура виписки описана один раз (`Department.discharge`, метод `final`).
- [x] У `Department`/`Ward`-подібному коді немає `if/switch` за назвою відділення: `grep -E "switch|instanceof|getClass"` — порожньо.
- [x] `Department` не посилається на жоден конкретний клас документа (`grep` по іменах `Epicrisis` — порожньо).
- [x] Нове відділення (педіатрія) додане лише новими файлами.

### Завдання 2 — Builder
- [x] Неповний об'єкт отримати неможливо: конструктор `Referral` не public, єдиний шлях — `build()`.
- [x] Перевіряються пацієнт, ≥ 1 дослідження, підпис; повідомлення збігається з текстом із завдання.
- [x] `Referral` незмінний: поля `final`, списки — `List.copyOf`.
- [x] Типові направлення (передопераційне, профогляд) задані в одному місці — `ReferralDirector`.
- ⚠️ Нюанс: `StandardReferralBuilder` після `build()` не скидає стан. У коді кожне направлення будується новим екземпляром будівельника; для повторного використання одного будівельника знадобиться метод `reset()`.

### Завдання 3 — Abstract Factory
- [x] Змішати вироби різних категорій неможливо: усі три вироби створює одна фабрика.
- [x] `Ward` не імпортує й не згадує конкретних виробів/фабрик.
- [x] Категорія «новонароджені» додана 4 новими класами; `Ward` не змінювався.
- ⚠️ Нюанс: вибір фабрики за віком пацієнта робить раннер (`Main`), а не палата — так і задумано (клієнт отримує готову фабрику). У реальній системі вибір варто винести в один реєстр/конфігурацію.

## 4. Питання для захисту (підготовка)

1. **Чому `discharge()` оголошено `final`?** Щоб підкласи не могли змінити порядок кроків — міняти можна лише фабричний метод.
2. **Чим Factory Method відрізняється від простого `if/switch` у фабриці?** Switch змушує редагувати загальний код при кожному новому відділенні (порушення OCP); Factory Method розширюється новими підкласами.
3. **Навіщо Director, якщо є Builder?** Послідовність кроків типових направлень описана в одному місці й повторно використовується; клієнт не дублює ланцюжки викликів.
4. **Чому `Referral` без setter-ів?** Після формування направлення не змінюється (вимога), а незмінний об'єкт безпечніший.
5. **Що робить Abstract Factory «узгодженою»?** Усі `create*()` однієї фабрики повертають вироби однієї категорії; клієнт не може вибрати виріб в обхід фабрики.
6. **Що довелося б змінити без шаблонів при додаванні «новонароджених»?** Кожен `if` за віком у коді палати — саме це завдання усуває.
